## Strategy Gene

- **Domain**: video segment generation, model routing, prompt execution, reference handling, audio-lineage handoff
- **Summary**: Generate the required video segment assets from a locked production plan while preserving reference coverage, spoken-source decisions, and a complete handoff for assembly.
- **Reference Read Order**:
  1. Read `references/video-models-routing.md` before every model/provider/mode decision and before changing models on fallback.
  2. Read `references/voice-strategy-execution.md` before any prompt or tool call involving spoken audio, visible speakers, `audio_list`, or post-produced VO.
  3. Read `references/video-generation-execution.md` before writing prompts, splitting sequences, choosing parallel/serial generation, or planning BGM/audio sync. When handoff has `frame_chain_mode: pre_planned`, read the **Pre-Planned Frame Chain** subsection there first.
  4. Read `references/image-generation-guide.md` before any supplementary image/key-frame generation (frame-chain nodes: GPT Image 2 batch in subject-asset Step 4b, not ad-hoc in generation).
  5. When `parallel_continuity_activation: true`, align junction behavior with script-skill `references/editing-rhythm-design.md` §7-§8 (same titles as assembly mirror).
- **Tool Use Logic**:
  1. Use `video_generate` only after provider, model, mode, provider_param key, reference lists, duration, and sound strategy match the routing reference.
  2. Use `image_generate` only for justified supplementary references or key frames; never replace user-provided subject/product references with prompt-only images.
  3. Use `get_file_info` to refresh asset metadata/URLs, not as proof that a generated segment satisfies timing or audio lineage.
  4. Use `video-editor__ffprobe` or a duration-capable metadata path after generation to record actual segment duration before handoff.
- **Decision Principles**:
  1. Every required sequence needs its own successful returned asset or an explicit replan. Do not fill missing time by duplicating or stretching a different segment.
  2. Every spoken line has one planned source: co-generated dialogue, `audio_list_tts`, or post-produced VO. The source decision is binding through handoff.
  3. If planned VO will not fit a visual window, shorten the copy or revise timing before handoff. Never rely on assembly trimming VO.
  4. Media/reference coverage beats prompt optimism. If references are required for identity, product, style, or scene continuity, include them in the tool call and name their roles in the prompt.
  5. Text-layer ownership beats prompt convenience. Readable text must come from its declared owner, not from casual video-prompt wording.
  6. Fail closed on under-specified execution strategy, missing required references, invalid tool parameter contracts, unclear audio lineage, or unclear text-layer lineage.

# Usage

**Input**: A locked production plan from script-skill (sequence breakdown, production model, strategy, and Subject Element Brief), plus the Subject Anchor Plan and per-sequence reference map from subject-asset-skill. The Subject Anchor Plan is the source of truth for which `character_ref`, `prop_ref`, `scene_ref`, `product_ref`, `style_ref`, `ui_ref`, or key-frame assets must be used in each sequence. Optionally, input may include a concept preview (with extracted key frames), supplementary reference assets, and user reference image/video/audio.

**Continuity / frame-chain handoff** (field names must match script-skill Step 6c canonical schema exactly):

| Source | Field | Type / notes |
|--------|-------|----------------|
| script 6b | `parallel_continuity_activation` | `true` |
| script 6b | `junction_link_mode` | `pre_planned_stills` \| `tail_extract_junction` \| `anchor_text_only` \| `serial_video_list` |
| script 6b | `user_production_intent` | `{ continuity_strict, quality_tier, storyboard_control }` |
| script 6b | `global_style_lock` | string |
| script 6b | `segment_contracts` | `[{ sequence_id, entry_anchor, exit_anchor }]` |
| script 6b | `bridge_plan` | optional array |
| script 6c | `frame_chain_mode` | `pre_planned` |
| script 6c | `frame_chain_plan.in_segment_still_density` | `standard` \| `high` |
| script 6c | `frame_chain_plan.chain_nodes` | `[{ id, binds }]` |
| script 6c | `frame_chain_plan.per_sequence_slots` | `[{ sequence_id, slot_node_ids[] }]` |
| subject-asset 4b | `frame_chain_manifest` | map: `chain_nodes[].id` → `asset://` (and every `slot_node_ids` entry must resolve) |

**Payload build rule:** For each `sequence_id`, `image_list` order = `per_sequence_slots[].slot_node_ids` order; URL at position i = `frame_chain_manifest[slot_node_ids[i]]`. Prompt uses Seedance positional syntax only (`"image 1"` … `"image N"`).

Routing hints from brainstorm (`continuity_intent: high`, `frame_chain_recommended: true`) are **not** sufficient to run frame chain — they trigger a return to script-skill if execution fields are missing.

**Note on images**: All images are plain references - no first-frame/end-frame distinction at the API level; describe first-frame intent in the prompt and bind **positional** roles (`image 1` = entry, `image {last}` = exit) when `frame_chain_mode: pre_planned`. See **references/video-generation-execution.md** — Pre-Planned Frame Chain; script **references/editing-rhythm-design.md** §8.

**Audio strategy**: Audio co-generation is the #1 priority - SFX and on-screen dialogue are always co-generated in the video generation call, never post-produced. Before generation, every sequence must explicitly declare one primary **audio narrative mode**: `on_camera_sync_speech`, `voiceover_narration`, `silent_broll_with_text`, or `nat_sound_only`. See **references/video-generation-execution.md** Section I (Audio Strategy) and **references/voice-strategy-execution.md** for generation-stage spoken-source hard stops.

**PREREQUISITE CHECK**: Before starting any generation, verify that the execution strategy is sufficiently specified. At minimum: hard user constraints, `shot_strategy`, `audio_strategy`, `consistency_strategy`, and `fallback_strategy`. If upstream skills did not provide them, **route to script-skill** (abbreviated path is OK) — do not silently improvise a full multi-segment plan in generation-skill. Exception: single-sequence simple requests may use the STORYBOARD CONFIRMATION PROTOCOL below.

**CONTINUITY ROUTING GATE** (before multi-segment `video_generate`, >=2 sequences, parallel/hybrid):
- If **any** apply: brainstorm `frame_chain_recommended: true` or `continuity_intent: high`; user brief demands seamless joins / cinematic storyboard / open-end frames; or `production_strategy` is parallel with cross-segment story continuity —
- **AND** handoff lacks `parallel_continuity_activation` + (`junction_link_mode` or explicit `anchor_text_only` choice) —
- **BLOCK** and return to **script-skill** to emit Step 6b (and Step 6c if frame chain criteria match). Do not start parallel video generation from prompt text alone.
- If `frame_chain_mode: pre_planned` is set but `frame_chain_plan` or subject-asset `frame_chain_manifest` is missing, **BLOCK** Phase B; complete subject-asset Step 4b first.

**SUBJECT COVERAGE PREREQUISITE**: Before any multi-sequence generation, receive the Subject Element Brief plus a Subject Anchor Plan / `Subject Coverage Manifest` from subject-asset-skill. For every recurring visible character/person/product/object/location, the manifest must list `subject_id`, `visible_in_sequences`, `required_ref_type`, `ref_asset`, and per-sequence payload expectations. If a recurring visible subject has no `ref_asset`, return to subject-asset-skill to generate/derive the missing reference or explicitly replan the story so the subject no longer recurs. Do not proceed with prompt-only identity descriptions such as "same presenter" or "same young man" across independent calls.

**STORYBOARD CONFIRMATION PROTOCOL** (applies only when **single-sequence** or genuinely simple scope — no multi-segment parallel continuity requirement):

When the user provides a brief with reference images and format confirmation, and no upstream plan exists, follow this lightweight confirmation protocol before generating video. **Do not use this protocol to bypass script-skill** when the piece has **>=2 segments** and seamless/cinematic/storyboard continuity intent — run script-skill (abbreviated) + subject-asset + frame chain first.

1. **Present the sequence plan as text** - include the Scene Reference -> Sequence Mapping table (Rule 2) and a one-line description per sequence. Ask if the direction is OK. **Do not generate storyboard images by default** - text descriptions are sufficient for direction alignment. Only generate storyboard key frames if the user explicitly requests visual previews.

2. **If storyboard images are generated**: Collect feedback. The user may confirm the direction, request scene changes, or flag character appearance issues. **Separate scene direction from character appearance**: if the user's feedback is solely about the character (not the scenes), fix the character reference image once and proceed to video generation - do not regenerate all storyboard frames.

3. **Maximum 2 confirmation rounds**: After the user has confirmed the scene direction (even implicitly - e.g., feedback is only about character details, not scene content), proceed to video generation. Minor character adjustments (remove accessories, clean up details) should be resolved in a single character reference fix, not through additional storyboard rounds.

4. **Anti-loop detection**: If 2+ consecutive user messages address only character appearance and not scene direction, the scene direction is implicitly confirmed. Consolidate all character feedback into one reference image fix, then immediately start video generation.

**Output**: All generated video segments (with their sound-on/off status), plus the Voice Strategy Declaration and BGM Timing Mode Declaration as planning artifacts. These are handed off to **assembly-skill** for timeline assembly, audio production (TTS/BGM), mixing, cover bake-in, and final delivery. **Never expose internal production terms** (sequence numbers, generation modes, sound on/off, model names) to the user - use natural creative language.

**Required asset manifest**: Maintain one manifest row per required sequence throughout generation. The canonical handoff fields and blocking rules are defined in **Assembly Handoff**.

## Degraded Execution Declaration

When using a non-ideal path due to model or tool limits, record it explicitly in working context before handoff.

Examples:

- `degraded_mode: segmented_continuation`
- `degraded_mode: post_produced_voice`
- `degraded_mode: weak_consistency_locking`

A degraded path is allowed if it does not directly violate hard user constraints. The key requirement is to make the compromise visible so downstream assembly and QA can evaluate it correctly.

**Constraints & Behavior**:

1. **Model selection**: Execute using the model recommended by script-skill. The four-layer routing system, tool call mapping, and decision tree are defined in **references/video-models-routing.md** Section I - verify every `video_generate` call against that definitive reference before submission.
   - **Pre-call model verification** (mandatory): Before every `video_generate` call, confirm `provider`, `model`, `mode`, and `provider_param` key all match the routing decision per the mapping table in **references/video-models-routing.md** Section I. Mismatching any field is a critical error.
   - **Reference-discard check**: If user-uploaded reference materials exist and the call uses `mode: "text2video"`, STOP - `text2video` cannot accept `image_list`/`video_list`/`audio_list`. Re-route to Seedance or Kling with `reference2video`.
   - **Image-list population check**: When user-uploaded images exist and the production model supports references, `image_list` MUST contain at least the user's primary reference image.
   - **Sound-off sanity check** (mandatory before every `video_generate` call with `sound: "off"`): Verify that the prompt does NOT describe visible speaking, singing, talking, vocalizing, presenting, or any mouth-movement-producing action. If the prompt contains on-screen dialogue cues (character speaking to camera, talking, singing, announcing, reading aloud, delivering a message, recording a greeting) AND sound is off, this is a **critical error** - the Voice Strategy Declaration was either skipped or incorrectly resolved. STOP, re-run the Voice Strategy Declaration (Rule 2, Steps 1-3), and correct the sound parameter before submitting the call. On-screen dialogue with `sound: "off"` produces decorative lip movements that cannot sync with any post-assembly audio - the result is always an audio-visual mismatch. **This check also applies when replicating a previous project's approach** - prior execution history is reference context, not a substitute for the Voice Strategy Declaration on the current project.
   - **`audio_list` duration-lock check** (mandatory before every `video_generate` call that uses `audio_list` for visible speaking / lipsync): Treat the source audio as the primary clock. Do **not** set `duration` longer than the referenced speech audio. If the model can infer timing from the audio, prefer omitting `duration` rather than forcing a longer whole-second target. If a specific target duration is creatively required, first edit/retime the audio itself to that target and then pass the retimed audio file - never use a 6s speech asset to drive an 8s talking-head clip and then re-attach the original 6s file in assembly.
   - **`audio_list` sync-clock ownership check** (mandatory for visible speaking, singing, lyrics, or music-video performance): after generation, the returned video's embedded/native audio is the only verified audio clock for the generated mouth/body timing unless the provider explicitly guarantees exact source-waveform passthrough. Handoff must mark `sync_clock_source: embedded_generated_video_audio`, `source_audio_asset`, and `native_audio_must_be_preserved: true`. Do not plan to mute the returned video and reattach the original master audio in assembly as a hidden cleanup step; that creates mouth/source drift even when durations are close.
   - **Visible-speech payload assertion** (mandatory before every `video_generate` call): compare the Voice Source Declaration against the actual payload. If any line for this sequence has `planned_source: audio_list_tts`, the provider param MUST contain `audio_list` with that returned speech asset before the call is submitted. If the TTS asset has not returned, wait. If the asset exists but is not in `audio_list`, STOP and rebuild the payload. Do not silently degrade to an open-ended prompt such as "speaking naturally" or to post-produced VO.
   - **Seedance audio_list companion-reference gate**: Seedance cannot use `audio_list` as the sole reference input. If a visible line is declared `audio_list_tts` but the case has no image/video reference for that sequence, choose and record one of these paths before generation: (a) generate/derive a presenter or key-frame visual reference, then call `video_generate` with `image_list + audio_list`; (b) switch to exact quoted co-generated dialogue in the prompt when same-voice continuity is not required; or (c) explicitly replan the shot as silent/non-speaking B-roll with the required override fields. The call is BLOCKED until the chosen path is reflected in the payload and handoff.
   - **Recurring-subject payload gate**: Before every `video_generate` call, compare the Subject Coverage Manifest against the exact payload. If the sequence contains a recurring visible subject, that subject's `ref_asset` MUST be present in `image_list` or `video_list`, and the prompt must bind it by position/filename with its role (`character_ref`, `product_ref`, etc.). Missing payload refs are a blocking error even if the prompt says "same man", "same presenter", "same product", "returns", or "continues".
   - Generation-skill only overrides the model on degradation (see Rule 12).
2. **Build the Production Blueprint**: Break the brief into an executable **Sequence** list. When **Grok** is selected, the plan is a single sequence; write one flowing narrative prompt per Grok's style. Each sequence represents a **self-contained narrative paragraph containing multiple shots** (see **references/video-generation-execution.md** Section III). Duration per sequence depends on the production model: **Seedance <=15s**, **Kling <=10s**, **Grok <=10s**. **Single-call preference** (see **references/video-generation-execution.md** Section II): When total video duration fits within the model's single-call max, strongly prefer generating the entire video in one call - use prompt-internal timing cues (`[0-5s]`, `[5-10s]`, `[10-15s]`) to structure beats within a single prompt. This avoids unnecessary cross-segment consistency risk, redundant API calls, and post-assembly overhead. Split only when there is a clear production reason (independent scenes needing different references, isolated retry needs). For multi-sequence videos, leverage Seedance's 15s cap to reduce sequence count and cross-sequence consistency risk - let narrative rhythm determine natural break points within the model's limit. Plan all sequences upfront before generating any - map the full narrative arc first, then write individual prompts. End at a natural pause point so sequences can chain cleanly.
   - **Shot duration heuristics** - when the sequence includes voiceover or on-screen text:
     - **VO/text coverage**: Budget shot duration >= spoken/read duration + 0.5-1s slack (~3-4 Chinese chars/sec, ~2.5-3 English words/sec). When planning a sequence that hosts voiceover/narration, budget the sequence duration to be **at least** the estimated VO read time + 1s - never shorter. Example: a 20-character Chinese voiceover at 3-4 chars/sec needs 5-7s of speaking time; do not assign it to a 4s sequence. For English VO, treat a 15s target as roughly 35-42 spoken words after pauses/emphasis; denser product explainers must be rewritten before generation. If the narrative structure constrains the sequence to a shorter duration, shorten the VO text to fit the available time.
     - **Single-sequence VO fit gate**: The single-call preference does not override VO fit. If a 15s Seedance video uses post-produced VO, the planned VO copy must fit the 15s target before generation starts. If it does not fit, shorten the copy or revise the duration; do not send an overlong VO plan downstream expecting assembly to trim it.
     - **Audio-driven talking-head exception**: When visible speech is driven by a provided speech asset via `audio_list`, the sequence duration must follow that asset's real duration - not a padded storyboard beat. Small tail room is acceptable only if it is intentionally baked into the audio file itself. Do not plan extra silent hold time after a lipsynced line unless you generate a separate visual-only tail segment.
     - **Breathing room**: ~0.5-1s between narrated shots, ~1.5-2s visual-only between narrated sequences.
     - **Shots without narration** follow emotional weight rather than text timing - see `references/editing-rhythm-design.md` Section 4.
     - Sub-second precision is below model resolution - use timing cues as pacing guidance.
   - **Visual Intent Pass** (multi-sequence only): Before writing any individual prompt, establish a unified visual language using the **Visual Style Convention** (4 constants: rendering style, color palette, lighting mood, texture quality) from the script-skill handoff. These constants become a **style preamble** prepended to every segment's prompt - this prevents each segment from independently interpreting the visual style. Verify adjacent segments for unintentional style drift before writing prompts.
   - **Junction link mode router** (from script `junction_link_mode` — resolve before any multi-segment video work):

     | Mode | Default? | What to do |
     |------|----------|------------|
     | `pre_planned_stills` | Yes when `frame_chain_mode: pre_planned` | Phase A: one GPT Image 2 batch for `frame_chain_plan` nodes (+ optional MID). Phase B: one parallel `video_generate` batch. **Do not** extract junction stills from video before Phase B. |
     | `tail_extract_junction` | Only when user rejects storyboard junction stills or demands pixel match to generated output | May generate upstream segment(s) first for affected junction(s), extract PNG from final ~0.5s, assign as next segment `image_list[0]`, then generate downstream. Slower; partial serialization only where required. |
     | `anchor_text_only` | Light Step 6b without frame chain | Shared refs + anchor copy in prompts; no `frame_chain_plan` gate. |
     | `serial_video_list` | Continuous same-scene action block | Seedance `video_list` continuation — not combined with `pre_planned_stills` on the same junction. |

     **Tail-frame extraction** (keep): use when `junction_link_mode: tail_extract_junction`, or as **repair** after pre-planned junction QA fails, or when user explicitly asks to use the actual last generated frame. Never use as the silent default when `pre_planned_stills` is selected.

   - **Parallel Continuity Gate** (when `parallel_continuity_activation: true`): Before parallel `video_generate`, verify anchors + style lock + per-segment camera move intent. If `frame_chain_mode: pre_planned`, also run **Frame Chain Gate** below.

   - **Frame Chain Gate** (when `frame_chain_mode: pre_planned`): BLOCK Phase B unless:
     - `frame_chain_plan.chain_nodes`, `frame_chain_plan.per_sequence_slots`, and `frame_chain_plan.in_segment_still_density` are all present.
     - Every `sequence_id` in `required_sequence_manifest` has one `per_sequence_slots` row.
     - `frame_chain_manifest` resolves **every** id in every `slot_node_ids` list.
     - Junction check: for adjacent seq A → B, `per_sequence_slots[B].slot_node_ids[0] === per_sequence_slots[A].slot_node_ids[-1]` and both map to the **same** `asset://` in `frame_chain_manifest`.
     - Built `image_list` length equals `slot_node_ids` length; order matches exactly.
     - Each segment prompt: `"image 1"` = entry role for `slot_node_ids[0]`; `"image {N}"` = exit role for `slot_node_ids[-1]`; journey 1→N; declare each MID id if `frame_chain_plan.in_segment_still_density: high`.
     - No `video_list` for cross-segment joins in this block.

     Prompt skeleton (pre-planned): `Global style: {lock}. Image 1: entry/opening. Image {last}: exit/ending. Journey from image 1 to image {last}. Primary move: {move}.`

     Do not force assembly-only transitions into generation prompts unless the plan marks in-clip generated transitions.
   - **Visual Style Convention**:

     | Constant | Example | What it controls |
     |----------|---------|-----------------|
     | **Rendering style** | photorealistic / cinematic / painterly / illustration / motion graphics | The fundamental look - mixing styles across segments (e.g., nature macro -> CGI -> studio) is the #1 cause of visual disconnection |
     | **Color palette** | warm golden tones / cool desaturated / neutral with jade accents | Dominant color character - shifts of >2 stops between adjacent segments look like different videos |
     | **Lighting mood** | soft natural / dramatic rim light / studio even / golden hour | Lighting consistency is as important as color - a studio-lit segment adjacent to a natural-light segment breaks immersion |
     | **Texture quality** | organic film grain / clean digital / dreamy soft focus | Surface treatment - gritty next to polished reads as a style error, not variety |

     These 4 constants become a **style preamble** that is prepended to every segment's prompt. Example: "Cinematic photorealistic look, warm golden palette with jade accents, soft diffused natural lighting, organic film-like texture." This preamble is not optional - it is the mechanism that prevents each segment from independently interpreting the visual style.

     **Step 2 - Visual Intent Table** - one row per sequence:

     | Seq | Color Temperature | Shot Anchor | Human Relationship | Transition In | Cut link (montage only) | Narrative Justification |
     |-----|-------------------|-------------|--------------------|---------------|-------------------------|-------------------------|
     | ... | ...               | ...         | ...                | ...           | ...                     | ...                     |

     Rules for filling the table:
     - Every cell must contain an explicit absolute description (e.g., "cool overcast grey", "wide -> mid-shot", "two workers in conversation"). No cell may be left blank or marked "same as above."
     - Adjacent rows may share the same value when the narrative calls for continuity - but the justification cell must explain why (e.g., "maintains emotional momentum from seq2"). Similarity by default, not by intent, is what this step prevents.
     - Transitions: carry meaning beyond cut/no-cut - note the reason (e.g., "dissolve - 20-year time jump", "cut - same scene, momentum continuity"). Montage rows: fill **Cut link** with the planned motive in plain language; mirror it in prompt `[start-end]` beats (`references/editing-rhythm-design.md` §6). Never prompt only "quick cuts between scenes."
     - **Color Temperature** values must be consistent with the Style Convention's color palette. If a segment needs a different temperature (e.g., flashback in cool blue), the Narrative Justification must explain the shift, and the transition must signal it.
     - This table is produced once before any generation call. Because every row is self-contained with absolute values, it works identically for both serial and parallel generation.

     **Step 3 - Style Drift Check** (validate before writing prompts): Scan the completed table row by row. For each adjacent pair of segments, verify:
     - Would the two segments look like they belong in the same video? If segment A describes "macro nature photography in soft morning light" and segment B describes "CGI particle convergence in dark studio lighting," they will look like clips from two different projects.
     - If a style shift is intentional (e.g., reality -> fantasy transition), the Transition In cell must contain a transition type that signals the shift (dissolve, whiteout, motivated cut) and the Narrative Justification must explain why.
     - If a style shift is unintentional - the segments just ended up with different visual languages because they describe different subjects - **unify them** by rewriting both to share the Style Convention's constants. Different subjects can coexist within one visual language; different visual languages cannot.

     Prompts are written by translating each row's design decisions into language - not by re-inventing the visual design during prompt writing. **Every prompt starts with the Style Convention preamble**, followed by the segment-specific direction from the table row.
   - **Scene Reference Image Coverage** (mandatory when user provides multiple distinct scene/environment reference images):
     Count the number of distinct scene/environment reference images the user provided (different locations, backgrounds, or settings - not multiple angles of the same scene). The Production Blueprint must **use every user-provided scene reference image** - no image may be silently dropped.
     - **Mapping is flexible**: N scene reference images do NOT require N sequences. A single <=10s sequence can contain multiple scene transitions - pass multiple scene reference images into one sequence's `image_list` and describe the scene cuts in the prompt. Kling handles intelligent scene-splitting from text. Example: 3 scene references in a 10s sequence -> prompt describes a 3-location montage, image_list contains all 3 scene images plus the character reference.
     - **Sequence count is driven by duration and narrative, not reference count**: Plan sequences based on `target_duration / max_sequence_duration` and narrative arc, then distribute scene references across sequences. A 15s video with 4 scene references could be 2 sequences x ~8s (each covering 2 scenes) or 4 sequences x ~4s - the right split depends on pacing and transition design.
     - **Explicit mapping table** (include in plan output to user):
       | Seq | Scene References Used | Planned Duration |
       |-----|----------------------|-----------------|
       | 1   | Image 1 (street), Image 2 (station) | 8s |
       | 2   | Image 3 (bridge), Image 4 (temple) | 8s |
     - If any user-provided scene reference image is not mapped to a sequence, explain why in the plan.
     - This rule supplements, not replaces, the Visual Intent Table - the mapping table is a planning tool; the Visual Intent Table governs visual consistency.
   - **Speed-change segments**: When the creative brief calls for slow-motion or fast-motion within a segment, compute the required source window first: `required_source_ms = final_timeline_duration_ms x playback_speed`. Then choose a provider-legal source generation duration that is at least that source window. Example: 5s final at `0.5x` slow motion needs 2.5s of source. Kling create-video may use `duration:"3"` and then edit only `in_ms:0, out_ms:2500` at `speed:0.5`; Seedance must use at least `duration:"4"` and the same `0-2500ms` source window. Do not use the full rounded-up source duration unless you intentionally accept a longer final output or recalculate speed.
   - **Voice Strategy Declaration** (mandatory before generation - any video with spoken audio): Read `references/voice-strategy-execution.md` before writing generation prompts. Before writing any generation prompt, classify every spoken audio element in the creative brief and assign it to exactly one source. This declaration is binding - once a line is assigned to a source, it cannot also be produced by the other source.
     - **Step 0 - Declare the audio narrative mode per sequence**: Explicitly choose exactly one primary mode for each sequence: `on_camera_sync_speech`, `voiceover_narration`, `silent_broll_with_text`, or `nat_sound_only`.
       - `on_camera_sync_speech`: the visible person/character is intended to speak on screen; the line must come from generated or audio-driven in-scene speech, not a duplicate post-produced VO.
       - `voiceover_narration`: speech is off-screen narration; avoid strong visual speaking cues in the covered shots unless they are intentionally treated as muted B-roll.
       - `silent_broll_with_text`: no spoken layer is planned; meaning is carried by image, music, and/or text.
       - `nat_sound_only`: production sound / ambience / action sound is the primary audio; do not restate the same content via explanatory VO.
       - If a single moment appears to need two conflicting primary modes, STOP and resolve it in script logic before any generation call.
      - **Character-sync contradiction check**: If the original user request or locked plan ties the voice to a visible character's body, timing, gestures, mouth, or direct-camera performance, `voiceover_narration` is invalid unless the plan explicitly says the narrator is off-screen and the visible character is intentionally silent B-roll. Do not write speech-suppression instructions into a prompt under that condition. Re-route to `on_camera_sync_speech` with exact lines / `audio_list`, or ask one focused clarification before any `video_generate` call.
      - **Visible-speech prompt blocker**: Before every `video_generate` call, compare the original user request and script-skill `voice_source_declaration` against the prompt. If the viewer is meant to perceive the visible character as the speaker, the call is BLOCKED when the prompt suppresses speech or describes only a silent non-speaking performance. This block can be lifted only when all of these are true: `visible_speech_request_preserved: false`, `silent_broll_override_reason` is present, and `user_visible_speech_change_disclosed: true`. Otherwise route visible speech through exact prompt dialogue or `audio_list_tts`.
      - **Open-ended visible-speech payload blocker**: If a `video_generate` payload contains any visible speaking cue (`speaking`, `talking`, `presenting`, `explaining`, `lips moving`, `speaks to camera`, `continues speaking`, `natural speech`) and does not contain either (a) exact quoted dialogue in the intended spoken language or (b) a returned speech asset in `provider_param.*.audio_list`, the call is BLOCKED. Do not let the model invent presenter speech. If the user brief is Chinese and no other spoken language is specified, the intended spoken language is Chinese/Mandarin.
    - **Step 1 - Classify each spoken element by viewing relationship**, not by labels. Ask: who would the viewer believe is speaking, does the body/mouth/gesture need to be connected to the words, does this voice identity continue across shots, and must a supplied audio file remain the final audible source? Treat words like "voiceover", "narration", "dubbing", and "talking-head" as evidence only; they do not decide the route by themselves.
      - If a visible person or character is the communicative center and the words are perceived as their performance, choose on-screen dialogue/monologue and solve it during generation.
      - If the voice clearly sits outside the scene over B-roll, product detail, diagrams, montage, or non-speaking action, choose off-screen narration and keep the visual prompt free of speaking behavior.
      - If the same perceived speaker has both visible lines and off-screen narration across sequences, first preserve one voice identity. Use shared/per-line speech assets: visible lines through `audio_list`, off-screen lines as matching post VO.
      - If the user supplied audio, decide whether it is a final master, lip-sync driver, rhythm/mood driver, or voice identity reference. Do not assume all audio should simply be mixed into the final timeline.
      - Tie-breaker: when the intent could mean either character-coupled speech or generic VO, protect visible performance first. Post-produced narration can be added later; a visible mouth/body performance generated without the right voice cannot be repaired cleanly in assembly.
     - **Step 2 - Determine the voice routing** based on on-screen visibility and whether voice identity must be preserved across languages:
      - **On-screen dialogue / monologue** (character visibly speaks - any visual style including 2D animation, illustration, motion graphics, realistic): **Co-generate or audio_list path.** Include the exact dialogue/monologue in the sequence prompt (`sound: on`), or use `audio_list` when deterministic speech/lipsync or cross-sequence voice identity is required. Open-ended phrases like "begins speaking naturally", "continues speaking", "speaking naturally", "natural speech only", or "talks to camera" are not valid spoken-content contracts. Co-generation produces lip-synced, emotionally matched voice for self-contained lines only when exact spoken content and language are declared; `audio_list` is preferred when the same character's voice must match later/earlier TTS narration.
      - **Off-screen narration / voiceover** (no on-screen speaker): **TTS path.** `sound: on` for SFX only in the prompt (no speech). Avoid visible speaking cues; when a presenter/talking-head visual remains on screen, add an explicit speech exclusion such as `"no speech, no dialogue, no voice, no spoken words"`. Narration via `audio_produce` in post-assembly. This gives full voice control (consistent voice ID, pacing, tone) for narration that spans multiple sequences.
      - **Voiceover exclusion must be explicit and redundant**: When a sequence is declared `voiceover_narration` and `sound:on`, the generation prompt must explicitly ban generated speech in at least two phrasings, e.g. `"no speech, no dialogue, no spoken words, no narrator voice, sound effects and ambience only"`. Do not rely on `"no background music"` or generic SFX wording to imply a speech ban. Finance/news/explainer montage prompts are especially prone to accidental co-generated narration if speech is not explicitly excluded.
       - **Mixed: same video has both on-screen dialogue AND off-screen narration**: **Split path by speaker identity.** If the on-screen speaker and off-screen narrator are different narrative roles, on-screen dialogue may be co-generated and narration may use TTS. If they are the same character/person, preserve one voice identity: create a shared master/per-line TTS or reference-voice asset, pass visible lines via `audio_list` for lip sync, and place off-screen lines as post VO from the same voice identity. Do not accept timbre drift for the same speaker.
       - **Inner monologue with no visible lip movement** (character thinking, no mouth movement): **TTS path.** Treat as off-screen narration since there is no visual speaking action to synchronize with.
       - **Cross-language dubbing with voice preservation** (user wants the target-language speech to keep the same speaker / same character timbre as the source audio): **Reference-voice dubbing path.** Do **not** route this as ordinary generic TTS. First extract or isolate the source speech and treat it as a **voice identity reference anchor**. Then, if tooling supports it, generate the target-language speech with voice-clone / reference-conditioned TTS. If tooling does not support true voice preservation, explicitly tell the user before final delivery - never silently downgrade this request to arbitrary target-language TTS.
     - **Step 3 - Record the declaration** (internal, not shown to user): For each sequence, note the chosen audio narrative mode, `speaker_id` / `voice_identity_id`, which spoken lines go into the prompt (co-generate), which are driven by `audio_list_tts`, which are produced via `audio_produce` (TTS), and which are absent (SFX-only sequences). This declaration feeds directly into prompt writing (Rule 7) and the Assembly Handoff (Rule 10).
     - **Step 3b - Audio asset dependency gate**: When same-speaker visible speech and off-screen narration need one voice identity, visible lines planned as `audio_list_tts` create a hard dependency. Produce or receive the matching speech asset first, wait for its returned `asset://...`, then call `video_generate` with that asset in `audio_list`. Do not batch that `video_generate` in parallel with the `audio_produce` call it depends on. If the asset is missing, generation is blocked; do not replace the visible line with post VO or silent B-roll.
     - **Single-shot co-generation allowance**: If a visible spoken performance is self-contained inside one generation call, the total duration is within the model limit, no reused voice identity is required, and the user has not supplied or required a specific voice/audio source, direct co-generation with exact dialogue in the prompt is acceptable and often more natural than pre-producing TTS. Use `audio_list_tts` instead when exact voice identity, supplied audio, cross-shot continuity, or deterministic delivery matters.
     - **Anti-Doubling Hard Stop**: A spoken line MUST have exactly one audio source - enforced at **planning time**, not just assembly time. Before triggering any generation or TTS call, verify that each spoken line is assigned to exactly one source in the Step 3 declaration. If the same line appears in both a generation prompt (co-gen) and an `audio_produce` call (TTS), this is a planning error - cancel one path before any call is made. At assembly time: if both co-generated voice (embedded in video) and a TTS asset exist for the same spoken content, assembly is **blocked**. Remove one source before proceeding. See assembly-skill SKILL.md Rule 1 (DOUBLE-VOICING CHECK).
     - **Voiceover montage preflight**: Before any `video_generate` call declared `voiceover_narration`, compare the prompt and downstream plan together. If the plan also includes post-produced VO/TTS, the generation prompt must not contain any visible-speaking cues and must contain explicit speech exclusion language. If either condition fails, the call is BLOCKED because it creates a high-risk duplicate-speech path: generated narration plus post VO.
     - **Dubbing downgrade hard stop**: Requests for "same voice", "same speaker", "same character voice", "keep the original timbre", or "translate this speech into another language but keep the same voice" are **not equivalent** to ordinary narration requests. If the pipeline cannot perform reference-voice dubbing, stop and surface the limitation to the user instead of silently shipping a generic TTS voice.
   - **BGM Timing Mode Declaration** (mandatory for any video with BGM - decide before generation begins): Determine the temporal relationship between music and visuals. This decision affects generation order.
     - **Step 1 - Assess the creative brief's audio-visual relationship**:
       - Does the brief describe specific musical moments tied to visual events (beat drops on scene changes, rhythmic cuts, music swells at emotional peaks)? -> **video-first**: generate video segments first, analyze their actual rhythm, then compose BGM to match.
      - Does the user provide an audio track, or does the brief design the narrative around a musical arc (music video, dance choreography, audio-driven montage)? -> **music-first**: generate or analyze the audio first, then generate video segments with timing informed by the audio. **Current tool boundary**: today's `video-editor__analyze_audio` only gives `duration`, `bpm`, `lufs`, `lufs_range`, and `true_peak` - use it for tempo / loudness inspection, but do **not** assume beat timestamps or segment boundaries exist. **Seedance `audio_list` implementation** (when safe): pass the user's audio file via the `audio_list` parameter on the `video_generate` call (use the audio asset path returned by upstream tools) so Seedance can make visuals reactive to the input audio. Do NOT generate video without `audio_list` and then mix the audio in via `video-editor__execute_edit_video` when the user expects music-reactive visuals. **Hard boundary for vocal music**: if the audio contains vocals and the character visibly sings, the generated segment's embedded/native audio becomes the final sync clock. If the user requires the original master recording to remain the final audible track, stop and explain that this route may only provide approximate visual performance unless a waveform-preserving lip-sync tool/path is available. For long vocal songs, do not launch full-song generation until the pilot/confirmation gate below is satisfied.
       - Is the BGM purely ambient atmosphere with no expected sync to visual beats (background texture, mood layer, simple product showcase)? -> **independent**: generate BGM and video in parallel for speed.
     - **Step 2 - Record the mode** (internal): Note the chosen mode and reasoning. This feeds directly into execution order (Rule 6 for multi-sequence generation) and the Assembly Handoff (Rule 10).
     - **Long-form vocal music pilot gate**: Before any full-song visible-singing or lyric-mouth plan, verify script-skill's `music_lipsync_feasibility_declaration`. If missing, STOP and create/ask for it. If `track_duration_ms` exceeds the model single-call limit and `visible_vocal_performance=true`, full production is BLOCKED until a 10-15s pilot is generated and the user explicitly accepts the tradeoff: (a) original master audio with approximate mouth performance, (b) generated/native audio with better mouth sync but changed song/timbre, (c) silent visual performance, or (d) no production. Do not batch-generate many 15s clips for a full song before that acceptance.
     - **Generation budget gate**: If a music-first plan requires more than 3 `video_generate` calls, record `planned_generation_count`, `estimated_coverage_seconds`, `missing_segment_policy`, and `credit_risk`. Required `missing_segment_policy` must be `block_final_until_generated` unless the user explicitly asks for a rough preview. Never set it to "duplicate neighboring segment" for final delivery.
     - **Default**: For multi-sequence narrative videos (>10s), default to **video-first** unless the brief explicitly indicates music-led pacing. For single-segment videos (<=10s), default to **independent**. **Exception**: When the user provides instrumental BGM or non-vocal music as creative input, default to **music-first**. When the user provides a vocal song for visible singing/lyrics, default to the Long-form vocal music pilot gate, not automatic full music-first production.
     - See **references/video-generation-execution.md** Section IV (BGM Planning) for the full framework.
3. **Reference Mapping per Sequence** (mandatory before generation begins): Using the Subject Element Registry from subject-asset-skill, build a **per-sequence reference plan** - which assets go into each sequence's image list, and what role each plays.
   - For each sequence, identify which subject elements from the registry appear in that sequence's narrative.
   - Assign concrete assets: user uploads, concept preview key frames, supplementary generated images. Each asset gets a positional index (`image 1`, `image 2`, ...) that will be referenced in the prompt.
   - **Every image in the image list must be explicitly referenced in the prompt** - declare its role (product_ref, character_ref, style_ref, etc.) and what the model should extract from it. No orphaned references.
   - **Gap filling**: If the registry shows an element as "uncovered" or "text description," write a detailed textual description for it in the prompt. Use character budget on uncovered elements; save budget on covered elements by pointing to reference images instead of re-describing them.
   - **When image slots are limited** (see tool schema for exact capacity per scenario), prioritize: product_ref > character_ref > style_ref > environment_ref > packaging_ref. If a sequence needs more references than the limit allows, combine roles (one image can anchor both product and style) or compress lower-priority elements to text descriptions.
   - **User upload consistency anchor - never text2image what the user already provided**: When the user has uploaded reference images (character, scene, style, product), these images are the **single source of visual truth**. All derived assets must trace back to user uploads to maintain consistency:
     - **Permitted**: Directly use user uploads in `image_list` - highest consistency.
     - **Permitted**: Use `image2image` with a user upload as the source image (e.g., to place the character into a scene, to remove accessories, to adjust framing) - maintains consistency because the source image anchors the visual identity.
     - **Prohibited**: Use `text2image` to regenerate content that a user upload already covers - text descriptions cannot capture the full visual identity of the user's asset, and the model will produce a different interpretation. This applies to both character references and scene references. Even if the prompt describes the user's image in great detail, the text2image output will diverge from the original.
    - **When a referenced asset becomes unresolved**: Refresh the asset metadata/reference via `get_file_info`; do not regenerate the asset via `text2image`. Reference-resolution failures are transient infrastructure issues, not a reason to create a new (inconsistent) version of an existing asset.
  - **Refresh file info before generation calls**: Before issuing any batch of `video_generate` or `image_generate` calls that reference uploaded assets, call `get_file_info` for all referenced assets so the tool sees fresh `file` inputs. Do not rely on stale cached file info - unresolved file paths/inputs can cause avoidable "file not found" failures and unnecessary regeneration.
4. **Static Image Placement (no video generation needed)**: When script-skill marks a sequence as `static_image_placement: true` (typically title cards, end cards, or brand frames that need no motion), skip `video_generate` entirely. Produce the image via `image_generate` (or use an existing key frame / user upload) and pass it directly to assembly as a still-image clip. Assembly places it in the `kind=video` track as an image file held for the planned duration. Ken Burns motion (slow zoom/pan) can be achieved via `scale_kf` keyframes on the image clip without video generation. Record in the manifest: `generation_mode: static_image_placement`, `asset_type: image`, and the planned hold duration.
5. **Single-Sequence (<=10s Kling/Grok, <=15s Seedance)**: Use **create video** with reference images and **audio co-generation enabled** (`sound: "on"` for Seedance, `sound: on` for Kling) to produce video + synchronized audio together - **dialogue, monologue, and SFX/environment/atmosphere** are co-generated. **Music and voiceover/narration may also be co-generated only when the final user-facing output is this one single segment** and there is no expected later assembly, extension, or revision chain. If the segment may later be reused, extended, or assembled into a longer cut, keep music and voiceover in post. **Never split a single-sequence video into multiple calls**. Seedance supports `sound: "on"` even when `image_list`, `video_list`, or `audio_list` are provided - unlike Kling which forces silent output with reference video.
   - **User-provided audio check** (mandatory for single-sequence Seedance): If the user uploaded instrumental BGM, non-vocal music, or a sound reference and the production model is Seedance, include the audio file in `audio_list`. Seedance generates video with motion and rhythm reactive to the input audio - this produces superior audio-visual sync compared to mixing the audio in afterward via `video-editor__execute_edit_video`. When `audio_list` is provided, the prompt should NOT include `"no background music"` - the audio_list IS the music source, and the model should generate visuals synchronized to it. If the uploaded audio is a vocal song and the visible subject is expected to sing/mouth lyrics, treat it under the vocal music sync-clock rules above; do not promise exact original-master lyric sync.
   - **Key-frame control is optional, not default**: For a single-sequence reference-based video, do **not** automatically generate supplementary key frames. First attempt direct production using the user uploads as `character_ref` / `product_ref` / `scene_ref` and describe the state change in the video prompt.
   - **When a control key frame is justified**: Generate **one** supplementary key frame only when it materially reduces drift risk in a critical beat - e.g. a complex final worn state, assembled product payoff, transformation target state, or another high-stakes end frame whose visual relationship is not directly covered by the user uploads.
   - **Single-sequence key-frame cap**: Default cap is **0-1** supplementary key frames for a single-sequence video. Go beyond one only when multiple distinct high-risk visual states genuinely need independent control.
   - **Reference-led hard rule for supplementary key frames**: If the key frame concerns a subject/product already present in user uploads, the key frame must be derived from those uploads via direct reference inputs (`image2image` / reference-led image generation). **Never** generate that key frame via pure `text2image`.
6. **Multi-Sequence (>15s Seedance / >10s Kling)**: See **references/video-generation-execution.md** Section II for the full parallel/serial decision framework. **Parallel is the default** for speed. Serial is only for continuous unbroken action or same-scene frame-level continuity. Audio is **not** a factor - Seedance supports `sound: "on"` in serial continuation.
   - **User intent overrides**: Explicit requests for fast cuts / montage / multi-angle -> parallel regardless of action type.
   - **Parallel**: All sequences use create video with images only, `sound: "on"`. Sequences generated concurrently with shared reference images.
   - **Serial continuation**: Seedance: pass previous sequence as `video_list`, `sound: "on"`, <=15s. Kling: reference video forces silent - prefer converting to parallel with extracted key frames to preserve audio. Use relative camera motion descriptions across segments.
   - **Tail-frame extraction** (retain — not the default pre-planned path): Extract a **static image** (PNG/JPEG) from the sharpest frame in the final ~0.5s of a **completed** segment. Never pass MP4 into `image_list`. Never AI-regenerate the extracted frame.
     - **Use when:** `junction_link_mode: tail_extract_junction`; user asks to match actual generated last frame; or pre-planned junction QA failed after one regen attempt.
     - **Do not use when:** `junction_link_mode: pre_planned_stills` and Phase A Manifest is ready — proceed to parallel Phase B instead.
     - After extract: update `END_Sn` in Manifest, set as next segment `image_list[0]`, regenerate downstream segment(s) only.
   - **Pre-planned frame chain (parallel seamless):** When `frame_chain_mode: pre_planned`, complete all chain-node `image_generate` calls (GPT Image 2 preferred) in **one batch** before **one** parallel `video_generate` batch. See `references/video-generation-execution.md` — Pre-Planned Frame Chain.
   - **Parallel prerequisite - reference completeness check**: Before parallel generation, verify every cross-sequence subject element has a concrete visual reference. `style_ref` only counts for look - it does NOT count as character/environment identity coverage. If any element lacks a reference -> generate it first.
   - **Subject payload matrix**: Before issuing the batch, create an internal matrix of `sequence_id -> required_subject_refs -> payload_refs`. Every required recurring `character_ref` / `product_ref` must appear in every relevant sequence's `image_list` or `video_list`. If any row is missing a required ref, do not call `video_generate`; fix the payload or regenerate/derive the missing reference first.
   - **Late-reference invalidation**: If a new `character_ref`, `product_ref`, or identity-critical key frame is created after any sequence was already generated, scan all existing sequence assets. Any already-generated sequence that contains that subject but did not use the new reference is stale and must be regenerated with the reference before assembly handoff. Do not mix anchored and unanchored generations in one final edit.
   - **Single-segment fallback**: If one segment fails, fall back only that segment per the degradation chain. Do not switch all remaining segments.
   - **Required-segment failure gate**: If any required segment fails, assembly remains blocked until that segment is regenerated or the story is explicitly replanned and the manifest updated.
   - **EXECUTION MANDATE**: When parallel mode is selected, **issue all generation calls simultaneously in a single tool-call batch**. Never serialize independent calls. This applies to concept previews and image generation batches too.
   - **Audio handoff**: After all segments are generated, hand off to assembly-skill. SFX and on-screen dialogue are **always co-generated** - never post-produced. Do not re-generate co-generated audio; do not co-generate lines assigned to TTS.
7. **Reference Anchor Input** (when using Seedance or Kling with reference images): If a concept preview exists, **extract a representative key frame as a static image** and treat it as the **`style_ref` for every production sequence** - this is the visual style anchor that establishes color grading, lighting tone, and overall aesthetic. Pass it alongside the `product_ref` / `character_ref` images in every sequence's image_list. **The product reference image alone constrains content (what appears), not style (how it looks) - without the preview frame as style_ref, each sequence will independently interpret the visual style and produce an incoherent look across the video.** Extract the frame at the midpoint of the preview clip (where the visual tone is most established), not from the first or last frame (which may be transitional). **This frame must appear in every sequence's image_list, not just the first.** **Critical**: the image list only accepts image files (JPEG, PNG, WebP) - **never pass a video asset into the image list**; this will cause "Image format is invalid" errors. When only a video asset is available for reference, either: (a) use it as the **reference video** input (feature mode, <=10s), or (b) generate a static key frame image first, then pass the image. Do not pass a Grok-generated video directly as reference to Seedance or Kling - use extracted key frames instead. When references cannot cover all elements, generate supplementary reference images **before** starting generation - strong reference coverage is essential since parallel is the default mode. When using **Grok** for production (pure T2V, no assets), this step does not apply.
   - **Do not over-credit the style anchor**: A preview key frame or generated style frame stabilizes color, lighting, and mood. It does **not** reliably stabilize who the character is, what a recurring room specifically looks like, or how two people relate in a story beat. Treat `style_ref` as necessary but insufficient for story-driven multi-sequence generation.
   - **Single-still bootstrap prohibition**: Do not replace missing `character_ref` / `environment_ref` coverage by generating one generic style still and feeding it to every sequence. That pattern produces globally coherent color but locally generic scenes, drifting faces, and weak payoff shots.
   - **Completed-look key frame interpretation**: A generated or extracted "completed look" key frame is a **control anchor for a specific target state**, not a replacement for the original `character_ref` or `product_ref`. Keep the user uploads in the image list and assign distinct roles in the prompt.
   - **No silent reference break after `get_file_info`**: If `get_file_info` was called in preparation for a supplementary `image_generate`, the next `image_generate` call must actually include the referenced images as tool inputs. Do not refresh file info and then fall back to prompt-only `text2image` for the same covered subject.
7. **Prompt Writing**: Follow **references/video-generation-execution.md** Section III for the full prompt spec (layer priority, syntax per model, character limits, reference-first economy). Key execution rules unique to generation:
   - **Material reference syntax**: Seedance: positional (`"image 1"`, `"video 2"`). Kling: `<filename>`. Grok: `@filename`. Every image in the list must be referenced in the prompt with its role declared.
   - **SFX mandatory check**: Every `sound: on` prompt must contain at least one concrete SFX description tied to a visual action. Generic atmosphere words do not count.
   - **No co-generated BGM**: Every `sound: on` prompt in multi-sequence production must include `"no background music, no musical score, no musical instruments - sound effects and ambient audio only"`. **Exception**: when `audio_list` is provided (music-first mode), do NOT include this exclusion.
   - **Narration-safe sound-on prompts**: When the sequence mode is `voiceover_narration`, every `sound: on` prompt must also include an explicit speech ban, such as `"no speech, no dialogue, no spoken words, no narrator voice"`. `"No background music"` by itself is not sufficient; it does not stop the model from inventing spoken audio.
   - **SFX coherence** (multi-sequence): Define a shared ambient foundation across all segments. Plan SFX as a designed arc, not random per-segment choices.
   - **Character consistency**: Pass the same reference images to every sequence featuring the character. Describe only motion/expression/pose in prompt - not static visual attributes visible in the reference.
   - **Text is not identity control**: Repeating static descriptors such as age, ethnicity, shirt color, hair, or "same person" is supplemental only. It cannot replace a required `character_ref` for a recurring visible person.
   - **Brand logo avoidance**: Include `"no visible brand logos, no trademark symbols, plain unbranded clothing"` when generating characters with clothing/accessories.
   - **Product scale anchoring**: Every prompt with product-and-person interaction must contain a realistic scale statement.
   - **On-screen text / packaging**: Follow `references/packaging-keyframe-guide.md`. Never ask the video model to typeset readable text from prompt - always use a key frame reference image. Layer 2 elements (precise text) are not supported.
   - **Text Layer Payload Gate**: Before every `image_generate` or `video_generate` call, compare the actual prompt and payload against script-skill's `text_layer_declaration`.
     - `owner: layer1_keyframe` -> the readable text must be present in a key frame/reference image. The video prompt may say "the poster from image 2 appears on the wall"; it must not repeat the exact readable copy as raw words for the video model to draw.
     - `owner: timed_subtitle_artifact` or `ass_post_overlay` -> the video/image prompt must not request the same words as screen signage, title-card text, UI labels, or environmental copy.
     - `owner: forbidden_in_video_prompt` -> remove the text from the prompt and replace it with an illegible visual description, such as "blurred generic paperwork" or "abstract data panels with no readable text".
     - `owner: unsupported` -> stop and replan or disclose the limitation. Do not hide unsupported exact text inside a generation prompt.
   - **Prompt text scan**: Treat quoted phrases, all-caps slogans, "text reads", "words appear", "labeled", "caption says", "screen shows", "characters flash", certificates, badges, signs, dashboards, UI labels, product labels, prices, phone numbers, URLs, and brand taglines as readable-text payloads. If they are not backed by the declaration and a matching owner, the call is BLOCKED.
   - **Language/script lock**: If the brief or declaration is Chinese/CJK, prompts must not substitute English, pinyin, Latin-only branding, or English CTA copy for readable text unless the user explicitly requested that language. Incidental background text should be described as non-readable/abstract rather than English filler.
8. **Timeline vs Source Duration Enforcement**: User-provided shot timing (e.g., "[0-2s]", "[2-4s]") defines the final edit window, not necessarily the `video_generate.duration` value. Before every `video_generate` call, track both:
   - `final_timeline_duration_ms`: the target duration in the final assembled video.
   - `source_generation_duration_s`: the provider-legal generated source length.
   Provider constraints always override scripted sub-shot timing. For Seedance, `source_generation_duration_s` must be an integer string from `"4"` to `"15"`; if a scripted beat is shorter than 4s, generate a legal 4s source clip and record the assembly trim window (for example `final=2220ms`, `source_generation=4s`, `trim=0-2220ms`). For Kling create-video, 3s can be legal, but still verify against the exact provider/mode contract. Do not split a `<=15s` Seedance video into separate generation calls solely because the user supplied timestamp rows; use one Seedance call with prompt-internal timing cues unless there is a concrete reason to split. After generation, verify actual source durations and trim visual clips in assembly to match the user-confirmed total (+/-1s tolerance).
9. **Post-Generation Sanity Check** (multi-sequence, same character): After all sequences are generated and before assembly, do a **lightweight correctness check** - not a subjective quality review. Use `analyze_file_content` on one representative frame per sequence (mid-point) and verify only binary pass/fail criteria:
   - **Character present**: Does the character actually appear in the sequence? (Catches cases where the model ignored the reference entirely.)
   - **Identity anchor present**: For every recurring visible subject, did the sequence use the required reference asset in its generation payload? If no, the asset is stale and must be regenerated before assembly, regardless of visual appearance.
   - **Gross identity mismatch**: If representative frames clearly show a different person/product category from the required reference (e.g., different race/age/gender/body type for a recurring presenter), regenerate that sequence with the same reference images before handoff.
   - **Gross deformation**: Is the character's body structurally intact? (Catches severe artifacts like missing limbs, extra heads, melted faces - not subtle style drift.)
   - If either check fails on a sequence, re-generate that sequence once with the same reference images. Do not iterate beyond one retry - if the re-generation also fails the check, proceed with the best result and let the user decide.
   - Do **not** check for subjective quality (expression accuracy, motion smoothness, aesthetic preference) - that is the user's judgment, not a gate. The goal is to catch obvious errors without adding meaningful latency to the pipeline.
10. **Assembly Handoff** (after all video segments are generated and sanity-checked): Hand off to **assembly-skill** with:
   - All generated video segments (populate the `file` field with the actual asset file path returned by upstream tools; include each segment's actual duration and sound-on/off status)
   - **Required asset manifest** (mandatory): every planned required sequence, its returned file path, status, actual duration, expected spoken lines, and whether it may be omitted. Any `failed` or missing required row blocks assembly unless the story has been explicitly replanned. Do not fill missing time by duplicating, stretching, or substituting another sequence.
   - **Subject Coverage Manifest passthrough** (mandatory for recurring subjects): carry forward the `subject_id`, `ref_asset`, `visible_in_sequences`, and per-sequence payload proof. If any delivered sequence is stale because it was generated before the reference existed or without the required reference in payload, assembly handoff is BLOCKED until that sequence is regenerated or the story is explicitly replanned.
   - **Audio lineage per segment** (mandatory): For each segment, declare the audio source - `co-gen` (model generated SFX/dialogue from prompt), `audio_list_tts` (TTS file passed via `audio_list` for lipsync - audio is baked into the video), `audio_list_music` (music file passed via `audio_list`), or `silent` (sound off). This lineage feeds assembly-skill's mandatory AUDIO AUDIT step, which probes each segment before deciding whether to add VO/BGM tracks.
   - **Sync-clock handoff for `audio_list` visible performance** (mandatory): When `audio_list_tts` or `audio_list_music` drives visible mouth movement, singing, or lyric performance, add these fields to the manifest row: `source_audio_asset`, `sync_clock_source: embedded_generated_video_audio`, `native_audio_must_be_preserved: true`, and `do_not_replace_with_master_audio: true`. If the final deliverable must use the exact uploaded master audio instead, mark `exact_master_audio_required: true` and do not promise frame-accurate lipsync from this generation route without an explicit waveform-preserving tool/path.
   - Voice Strategy Declaration (which spoken lines are co-generated, which need TTS production, and each sequence's audio narrative mode)
   - **Voice Source Declaration passthrough** (mandatory): carry forward script-skill's per-line declaration, including exact text, `planned_source`, speaker visibility, generation requirement, assembly guard, and `requires_assembly_asr`. If generation changes any source decision, update the declaration before handoff. If a line uses `audio_list_tts`, mark `do_not_add_separate_vo: true`.
   - **Voice Source Payload Map** (mandatory for visible speech): for each visible spoken line, hand off `line_id`, `sequence_id`, `planned_source`, `source_audio_asset` when applicable, `payload_audio_list_present`, `payload_visual_reference_present`, and `fallback_path_used`. If `planned_source: audio_list_tts` and either payload flag is false, assembly handoff is BLOCKED because the generated media cannot be trusted to match the declared voice strategy.
   - **Text Layer Declaration passthrough** (mandatory): carry forward script-skill's text rows, including owner, exact copy, language/script, sequence/time window, and collision policy. If generation creates or changes any text-bearing key frame, update the row before handoff.
   - **Visual Text Audit** (mandatory when any prompt, key frame, or scene contains possible readable text): list every known or suspected baked visual text element, its language/script, owning asset, source (`declared_layer1_keyframe`, `prompt_requested`, `incidental_model_output`, or `unknown`), and whether assembly must skip subtitles or run visual text detection in that window. If a Chinese/CJK brief produced English/pinyin baked text that was not explicitly requested, assembly handoff is BLOCKED pending regeneration or a documented user-facing limitation.
   - BGM Timing Mode Declaration (video-first / music-first / independent)
   - Creative script audio direction (VO copy, BGM descriptions, SFX notes)
   - Transition recommendations from the production plan
   - Cover source candidates (concept preview key frames, style_ref images)
   
   Assembly-skill owns: TTS/VO production, BGM production, timeline assembly with transitions, audio mixing and volume management, duration enforcement, cover bake-in, and non-generative edits. **Re-read `assembly-skill/SKILL.md`** before writing any edit spec - the mandatory AUDIO AUDIT, media-fact inspection, and anti-doubling checks cannot be executed from memory. Assembly will verify that any declared BGM plan has a matching music_generate output -- if BGM is planned but not produced, assembly is blocked.
   
   **Explicit voiceover copy is binding**: User-provided or brief-provided narration lines are required deliverables. If the copy cannot fit the planned visual timing, mark assembly blocked until the copy is shortened or visuals are retimed; never hand off a plan that depends on trimming VO with `out_ms`.
   
   **No silent downgrade**: If voice or music generation is unavailable or fails, surface the limitation to the user rather than silently delivering an incomplete video.
11. **Scenario Routing**: Route each generation call based on the production model and input. See **references/video-models-routing.md** Section II for model-specific scenarios and capacity limits.
   - **Handoff first**: Start from the upstream production-model choice and only change course when there is a clear degradation reason from Rule 12.
   - **Closeup guidance**: A closeup, hand detail, face detail, product beauty shot, or general precision request does not automatically call for Kling.
   - **Preview continuity**: If the approved preview worked on Seedance and the same stylized identity and reference set remain in use, Seedance is often still the best production route unless a concrete issue appears.
   - **Creating new footage** -> create video. Seedance: `sound: "on"` regardless of reference type. Kling: sound on without reference video; always silent with reference video.
   - **Continuing from a previous sequence** -> Seedance: pass as `video_list` + `sound: "on"` (audio preserved). Kling: pass as reference video (always silent - prefer converting to parallel with ref images if audio must be preserved).
   - **Visual-only fixes** (restyle, re-skin) -> edit video (Kling only) - preserves structure and timing, sound off (can preserve original audio).
   - **Reference video provided by user** -> Seedance: use as `video_list` with `sound: "on"`. Kling: use as reference video, accept silent output.
12. **Fallback & Degradation**: When the selected production model fails, follow the degradation chain in **references/video-models-routing.md** Section III. Key principles:
   - **Audio co-generation must be preserved** - never degrade to post-production SFX or dialogue. If audio co-gen fails: retry with reference images only (extract key frames from video), then change strategy and inform user.
   - **Document the reason before switching models** - if execution moves from Seedance to Kling, note the concrete trigger in the working state before the next `video_generate` call. Reasons like `closeup`, `real face`, `detail`, or `better quality` are usually too vague on their own; valid triggers include copyrighted-IP rejection, readable text/UI requirements, micro-detail accuracy, or a documented Seedance generation failure.
   - **Reference preservation is a hard rule** - when converting from reference video to reference images during degradation, always extract key frames from the video or use user originals. Never AI-regenerate. Never lose visual consistency.
   - **Sequence splitting on Kling degradation** - when a Seedance sequence (<=15s) must degrade to Kling (max 10s), split into 2+ Kling-compatible sequences, prefer parallel for audio preservation.
   - **Inform user** on significant mid-production changes - briefly, in natural language, not technical terms.
13. **Image Prompt Preflight** (before every `image_generate` call):
   - **Technical parameters never belong in prompt text**: Do **not** include aspect ratios (`9:16`, `16:9`), pixel sizes (`1920x1080`), quality labels (`4K`, `HD`), hex/RGB color codes, internal IDs, case numbers, or other metadata in the prompt. These tokens are frequently rendered into the image as visible text.
   - **Provider-specific aspect handling is mandatory**: For Seedream, pass only mapped pixel sizes (`"1920x1080"`, `"1080x1920"`, `"1024x1024"`) via `size`; never pass ratio strings. For Gemini, pass ratio strings via `aspect_ratio`; never pass pixel dimensions there. Follow `references/image-generation-guide.md` exactly.
   - **Non-standard aspect ratios** (e.g., 1.91:1, 4:5, 2.35:1): Image generation only supports 16:9, 9:16, and 1:1. When the user requests an unsupported ratio, generate at the closest covering supported ratio and crop to exact target dimensions - see `references/image-generation-guide.md` "Non-Standard Aspect Ratios" for the full strategy. Do not repeatedly regenerate at a standard ratio expecting the model to fill a non-standard canvas.
   - **Natural-language color descriptions only**: Replace `#000840` / `rgb(...)` style values with visual wording like `deep navy blue`, `warm amber`, or `soft jade green`. **This includes hex/RGB values from the user's own input** - when the user's brief specifies colors as hex codes (e.g., "background gradient #A2D2FF -> #B4F23C"), the agent can reason about those values internally (LLMs understand hex -> color mapping), but must translate them to natural descriptions before writing the image prompt (e.g., "soft sky-blue to pale lime-green gradient"). Never copy user-provided hex codes verbatim into image generation prompts.
   - **Final prompt sanity test**: Read the prompt once as if every token might be printed on the final image. If any remaining token would be embarrassing or obviously non-visual when rendered literally, rewrite before calling the tool.
   - **Brand/IP name prohibition in text2image**: Never include trademarked character or brand names (e.g., Labubu, Pop Mart, Hello Kitty, Disney, Sanrio, Pokemon) in `text2image` prompts - these consistently trigger content safety false positives across providers (observed: >60% failure rate with Seedream). Replace with purely visual descriptions. Note: when the user has uploaded the character image, `text2image` should not be used at all per Rule 3 - use `image2image` with the user's upload as the source, or pass the upload directly.

14. **Asset Organization** (before generation):
   - When assets exceed the tool's capacity limits per scenario, classify material vs. reference, budget material first, compress references to minimum effective dose.
   - **Seedance limits**: <=9 images in `image_list`, <=3 videos in `video_list` (total <=15s), <=3 audios in `audio_list` (total <=15s, requires at least 1 image or video). Seedance also supports audio references - when the user provides BGM or audio, pass as `audio_list` for audio-visual sync.
   - **Kling limits**: <=7 images (no ref video) or <=4 images (with ref video). Only 1 reference video per call, **must be <=10s**. Over-length videos must be trimmed.
   - When the user provides multiple videos, select the most relevant one; extract key frames from others to use as reference images.
   - Rank by role priority from the Subject Element Registry (product_ref > character_ref > style_ref > environment_ref). Keep within limits; silently drop lowest-priority items.
   - Decisions are autonomous - act like an editor curating raw material.
15. This stage focuses on producing video segments - **execute silently**. Never expose internal details to the user: sequence numbers, model names, routing decisions, prompt internals, or pipeline terminology. Use natural creative language for progress updates.
