# 搜索音色全链路与并发冲突下钻

**分析时间**：2026-08-14  
**生产窗口**：`2026-08-05T10:30:52Z` 至 `2026-08-13T16:00:00Z`  
**数据源**：Metabase production BigQuery database `2`，`pexo_ods.project_messages`  
**去重口径**：`project_id + tool_call_id` 取最新调用和最新结果  
**数据包**：`analysis/case-data/voice-search-concurrency-drilldown-2026-08-14/`

## 纠正后的结论

前面只看克隆音色是不完整的。线上实际有三段公共音色链路：

`voice_search` 搜索 -> `voice_preview` 试听 -> `audio_produce + voice_id` 正式生成。

“同一音色并发冲突”发生在第三段，即搜索得到公共音色后，系统把同一个 `voice_id` 同时用于多条台词生成。它不是克隆音色问题，也不是搜索接口本身的并发问题。

## 1. 完整链路规模

| 环节 | 调用 | 项目 | 结果 |
|---|---:|---:|---|
| 搜索音色 | 1,197 | 706 | 1,064 次成功返回候选，成功率 88.9% |
| 试听音色 | 894 | 235 | 847 次成功，成功率 94.7% |
| 公共音色正式生成 | 2,930 | 623 | 2,513 次成功；全调用成功率 85.8% |
| 克隆音色正式生成 | 568 | 51 | 376 次成功；与本报告的并发冲突是另一条链路 |

项目流转上，706 个搜索项目中：197 个走过“搜索 + 试听 + 正式生成”，415 个搜索后直接正式生成、没有调用试听，94 个没有进入公共音色正式生成。另有 11 个公共音色生成项目在窗口内没有搜索记录。

## 2. 并发冲突的频率和范围

公共音色正式生成共 2,930 次、623 个项目，其中：

- 167 次明确报 `Multiple voice additions/deletions for the same voice were called at the same time`；
- 涉及 55 个项目、64 个“项目 + 音色”组合；
- 调用发生率 `167 / 2,930 = 5.7%`；
- 项目发生率 `55 / 623 = 8.8%`；
- 在公共音色 209 次明确失败中，该错误占 `167 / 209 = 79.9%`。

167 次冲突前，全部能在同项目过去 24 小时找到成功的音色搜索。因此它明确属于“搜索音色进入正式生产后的批量生成问题”。其中 62 次、24 个项目还试听过同一个音色。

## 3. 用户会看到什么

冲突集中在 67 个同秒批次，单批最多同时发出 11 次同音色生成：

- 63/67 个批次同一秒内既有成功也有失败；
- 因此常见表现不是整批完全挂掉，而是“一组旁白里有几条生成成功、几条报错或缺失”；
- 如果编排层没有自动补齐，最终视频可能少一句旁白，或者用户需要等待重试。

按“同项目 + 同 voice_id + 完全相同台词”核对恢复：

- 164 条独立台词发生冲突；
- 156 条后来用相同台词和相同音色成功，恢复率 95.1%；
- 最快 11 秒，恢复中位数 29 秒，最慢约 2 小时 2 分钟；
- 仍有 8 条独立台词、涉及 6 个项目，没有观察到原样成功。

所以答案是：**重试大概率能成功，但不能把它当成无影响。** 当前是失败后被动重试，仍会产生延迟、重复调用，少量台词最终没有补齐。

## 4. 代表性线上 Case

以下 Case 都能证明所用音色来自此前成功的 `voice_search`，随后在 `audio_produce` 正式生成时失败。四个项目的失败结果完全一致：

- `error_code = media_orchestrator.execution_failed`
- `message = Multiple voice additions/deletions for the same voice were called at the same time. Please retry shortly.`

### Case A：`20601421896`，同一秒两个音色批次都出现部分失败

- 搜索证据：`2026-08-12 05:32:22 UTC` 搜索成功，结果包含随后使用的公共音色；搜索调用 ID `toolu_bdrk_01RZ9ruqDp6xeChpbbEaFVgC`。
- 正式生成：`05:36:49 UTC` 同一秒提交两个音色的多条台词。
- 音色 `6j8uSqQkZH2WrWDVIiRB`：11 次调用，8 次成功，3 次冲突；3 条失败台词在 17、23、31 秒后原样成功。
- 音色 `GorLj2SsI4u2JqL58gAA`：8 次调用，1 次成功，7 次冲突；7 条失败台词在 17 至 47 秒后原样成功。
- 原始调用示例：`toolu_bdrk_01UvfmYaeFg9V66VKsayFgoo` 生成 `...What the hell is this?` 时失败，17 秒后同音色、同台词成功。

**证据表现**：同一项目、同一音色、同一秒批量生成时，不是整批统一失败，而是留下少量成功、其余冲突。失败台词随后被拆批补齐。

### Case B：`53947316851`，高并发批次只成功 1 条

- 搜索证据：`2026-08-13 05:00:37 UTC` 搜索成功且结果包含音色 `igPb0GnUo3yZad5NmcoH`；搜索调用 ID `toolu_bdrk_01EnYEzD2ooUH6tJ5QrKYxiX`。
- 正式生成：`05:01:09 UTC` 同一秒用该音色提交 8 条台词，1 条成功、7 条冲突。
- 7 条失败台词后来全部原样成功，但恢复耗时为 70 至 127 秒。
- 原始调用示例：`toolu_bdrk_0157sYDqhgrhc2trV1PJBYXL` 首次失败，对应台词在 127 秒后才成功。

**证据表现**：重试最终能恢复，但对一组 8 条旁白来说，首次只产出 1 条，用户侧会长时间看到旁白不完整；这不是一次无感的瞬时错误。

### Case C：`61623092738`，部分失败台词没有观察到补齐

- 搜索证据：`2026-08-10 11:58:23 UTC` 搜索成功且结果包含音色 `spZS54yMfsj80VHtUQFY`；搜索调用 ID `toolu_bdrk_01B9WZbQ9748q2kmDLZRuWza`。
- 正式生成：`11:58:53 UTC` 同一秒提交 5 条台词，1 条成功、4 条冲突。
- 其中 2 条在 19 秒、35 秒后原样成功；另外 2 条直到恢复观察窗口结束仍没有同音色、同台词的成功记录。
- 未观察到原样恢复的调用 ID：`toolu_bdrk_01DVvLhUM2JLEmiruvyM5EMS`、`toolu_bdrk_01AKdSd37HUqPo5RF6vPPMXn`。

**证据表现**：自动重试并非必然补齐。遥测能确认两段正式旁白没有原样成功记录，存在交付缺句风险；是否被改写或从最终视频删去，需要再结合成片资产判断。

### Case D：`82198763068`，短间隔重试四次仍全部失败

- 搜索证据：`2026-08-13 14:51:43 UTC` 搜索成功且结果包含音色 `vhBIP7TzXaD17CYHAfIZ`；搜索调用 ID `toolu_bdrk_01ArQmTyRDUPsRZmLC3Ys5RQ`。
- 同一音色、同一台词分别在 `14:53:18`、`14:53:27`、`14:53:36`、`14:54:07 UTC` 重试。
- 四次调用都返回相同并发冲突，调用 ID 依次为 `toolu_bdrk_017Avc1bemEqGzJDWJkpeviL`、`toolu_bdrk_01Sm6VBv1tPLxJ4McuWRPcdD`、`toolu_bdrk_019RQd83AQYc7jjRqY7DkvQh`、`toolu_bdrk_013ypQfgZs5p8kV4cbCL8YBM`。
- 四次间隔为 9 秒、9 秒、31 秒；恢复观察窗口内没有同音色、同台词成功记录。

**证据表现**：每个时间点只看到 1 次该音色调用，但前一次失败后 9 至 31 秒内重试仍会冲突。这说明“把失败请求马上再发一次”不足以恢复，底层音色状态可能仍未释放，或者缺少对真实任务完成状态的确认。

### 从 Case 抽象出的共同触发模式

1. 用户先搜索到一个公共音色，系统随后用同一个 `voice_id` 生成多条独立旁白。
2. 编排层把多条正式 TTS 同时发出，底层却对同一音色执行了需要互斥的加入、配置或删除操作。
3. 同一批请求互相竞争，表现为部分成功、部分返回并发冲突；并不是音色内容或台词本身有问题。
4. 失败后立即重试可能继续撞上未释放状态；多数请求在延迟后恢复，但仍有少量台词未观察到原样成功。
5. 当前缺少三个保护：同音色任务队列或互斥、带退避的自动重试、整批台词完成度校验与缺失补齐。

## 5. 搜索和试听还有两类独立问题

### 搜索阶段

1,197 次搜索中：

- 1,064 次成功返回候选；
- 58 次缺失或无法解析结果；
- 44 次意图解析失败；
- 18 次请求条件不足；
- 8 次 Provider 失败；
- 5 次无匹配。

搜索接口没有出现上述“同一音色 additions/deletions”冲突。它的问题主要是解析失败、结果缺失，以及失败后是否擅自放宽用户条件。

### 试听阶段

894 次试听中有 40 次明确下载失败，涉及 26 个项目：

- HTTP 403：23 次；
- HTTP 404：13 次；
- HTTP 400：4 次；
- 另有 7 次结果缺失。

这是独立的“试听链接权限、有效期或 URL 可用性”问题，不应与正式 TTS 并发冲突合并提单。

## 6. 严重级别校准

“同一搜索音色并发生成冲突”建议定为 **P1，而不是 P0**：

- 频率不低：影响约 8.8% 的公共音色生成项目；
- 位于正式生产主链路，并占公共音色明确失败的 79.9%；
- 但 95.1% 的独立失败台词后来恢复，典型恢复时间约半分钟，不是全量不可用；
- 当前确认有 8 条台词、6 个项目未观察到原样恢复，存在真实交付缺口。

建议单独保留三个 Bug：

1. **P1：搜索音色批量 TTS 缺少同 voice 串行、幂等和失败补齐。**
2. **P1/P2：音色试听 URL 出现 400/403/404，缺少有效期与权限校验。**
3. **P1：音色搜索解析失败和结果缺失后，缺少约束保留与可追踪回执。**

克隆样本资产预检继续作为另一张 Bug 处理，不要把两个根因合成“音色并发”。
