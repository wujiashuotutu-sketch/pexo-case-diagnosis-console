# 音色克隆前置资产校验 P0 下钻

**分析时间**：2026-08-14  
**生产窗口**：`2026-08-05T10:30:52Z` 至 `2026-08-12T16:00:00Z`  
**数据源**：Metabase production BigQuery database `2`，`pexo_ods.project_messages`、`pexo_ods.projects`  
**去重口径**：`project_id + tool_call_id` 取最新调用和最新结果  
**数据包**：`analysis/case-data/voice-clone-preflight-drilldown-2026-08-14/`

## 结论

这个 P0 的准确表述不是“系统完全没有校验”，而是：

> `audio_produce` 已经会在每次调用内部检查资产解析、总时长、单文件大小和时长可解析性，但系统没有在批量 TTS 扇出前，对整组克隆样本做一次性预检、生成可复用 receipt，并在失败后熔断剩余台词。

结果是同一个确定性坏输入被复制到多条台词，之后才逐条失败。上线后 `543` 次克隆调用中，`174` 次是调用前即可判定的资产/样本失败，占克隆调用 `32.0%`、克隆明确失败 `94.6%`、全部 TTS 明确失败 `43.4%`。`36/48 = 75.0%` 的克隆项目命中过这类问题。

## 1. 克隆调用账本

| 结果 | 调用 | 占克隆调用 | 项目 |
|---|---:|---:|---:|
| 成功 | 355 | 65.4% | 36 |
| 资产引用错误或找不到 | 100 | 18.4% | 17 |
| 样本规格/解析失败 | 74 | 13.6% | 25 |
| Provider timeout | 9 | 1.7% | 2 |
| 文本超过 5,000 字符 | 1 | 0.2% | 1 |
| 缺失/不可解析结果 | 4 | 0.7% | 2 |
| **合计** | **543** | **100%** | **48** |

克隆明确失败为 `184` 次；其中资产引用和样本规格合计 `174/184 = 94.6%`。所以换供应商、增加重试或延长 timeout 都不是这一 P0 的主修复方向。

### 1.1 先回答“报错后能不能重试”

| 失败类型 | 原样重试 | 线上证据 | 正确恢复动作 |
|---|---|---|---|
| 资产找不到 | **不能** | 98 次失败中，没有观察到同一样本集合后来成功 | 重新导入当前项目或换成可解析的 canonical asset ID |
| `asset_id` 非法 | **不能** | 2 次失败，都是输入格式本身非法 | 重新选择或上传资产，不要修补原字符串 |
| 总时长不足 30 秒 | **不能** | 51 次失败，没有观察到同一样本集合后来成功 | 补充有效人声，使总时长达到 30 秒后重新预检 |
| 单文件超过 11MB | **不能** | 21 次失败，没有观察到同一样本集合后来成功 | 先提取音轨、压缩或拆分，保证每个文件不超过 11MB |
| 时长不可解析 | **不能** | 同一坏资产连续失败 2 次，没有恢复 | 重新转码并上传，确认系统能读出时长 |
| Provider timeout | **可以稍后重试** | 9 次失败属于 2 个样本组，两个组后来都用相同样本成功；最快恢复约 160 秒 | 先查任务状态，再用幂等键和退避重试 |
| 结果缺失/不可解析 | **不能直接判断** | 4 次调用后来同样本成功，但原任务究竟失败还是只丢了回执无法确认 | 先按任务 ID 查状态；确认没有成功产物后再重试 |
| 文本超过 5,000 字符 | **原样不能** | 1 次；后来成功不能证明原样恢复，因为后续文本可能已改变 | 拆分或缩短文本后重提 |

关键区别：前五类是**确定性输入错误**，输入不变就不要重试；timeout 是**暂时性服务错误**，可以退避重试；结果缺失是**状态未知**，必须先查状态，避免重复生成和重复计费。

## 2. 各失败类型逐项下钻

### 2.1 内部资产找不到：98 次，15 个项目

**是什么意思**：传入的样本路径指向另一个项目，当前运行环境没能把它解析成可用资产。98 次全部使用了跨项目 raw path；其中 11 次传入图片，11 次传入 MP4。

**为什么会发生**：调用方直接复用了 `/projects/<other-project>/...` 路径。这个路径不是稳定的资产身份：同用户跨项目 raw path 在窗口内既有成功也有失败，说明 runtime 解析行为不一致。

**重试是否有效**：无效。98 次中没有观察到同一样本集合在输入不变时后来成功；91 次已经是同一坏输入的重复提交，83 次集中在同一秒，最大同秒重复 10 次。

**正确恢复**：将源资产显式导入或复制到当前项目，或改用经过授权解析的 canonical asset ID，再重新做一次整组预检。不能继续提交原始跨项目路径。

**代表案例**：项目 `04339290687` 的同一跨项目 `IMG_7994.mp4` 在一秒内失败 10 次；项目 `28788643549` 把两张角色参考 PNG 当成音色样本，产生 11 次找不到资产的失败。

### 2.2 非法 `asset_id`：2 次，2 个项目

**是什么意思**：`asset://...` 看起来像资产引用，但 ID 长度或字符格式不符合合同，系统无法定位任何真实资产。

**为什么会发生**：上游手工拼接、截断或传入了占位值，没有在工具调用前验证 ID 结构。

**重试是否有效**：无效。这是字符串本身非法，不会随时间自动恢复；线上没有观察到原输入后来成功。

**正确恢复**：回到资产选择或上传环节重新取得真实 asset ID。产品应在批量 TTS 扇出前直接报 `ASSET_ID_INVALID`，而不是把非法 ID 传入每条 TTS。

### 2.3 样本总时长不足 30 秒：51 次，20 个项目

**是什么意思**：这一组可解析的音色样本加起来不到克隆要求的 30 秒。它不是网络问题，也不是 Provider 偶发失败。

**为什么会发生**：样本确实太短，或预期中的其他样本因路径/格式问题没有被计入有效时长。51 次中有 3 次使用跨项目路径，1 次直接传了 MP4。

**重试是否有效**：原样无效。没有观察到同一样本集合后来成功；30 次属于重复组，最大同一坏样本重复 6 次。

**正确恢复**：补充清晰、连续、以单人说话为主的有效人声，使可解析总时长达到至少 30 秒，然后重新预检。不能靠重复调用把 20 秒样本“重试成”30 秒。

**代表案例**：项目 `94317923362` 同时出现 18 次资产找不到和 17 次不足 30 秒，说明部分样本解析失败后，剩下的有效样本又不够长；编排层仍继续扇出整批台词。

### 2.4 单文件超过 11MB：21 次，5 个项目

**是什么意思**：不是整组总大小超限，而是至少一个样本文件本身超过 11MB。21 次失败全部传入 MP4，14 次还是跨项目 MP4。

**为什么会发生**：把视频文件直接当作音色样本，没有先提取和压缩音轨。视频容器包含画面，体积很容易超过声音克隆接口的单文件限制。

**重试是否有效**：原样无效。没有观察到同一样本集合后来成功；19 次属于重复组，最大重复 7 次。

**正确恢复**：先从 MP4 提取音频，转为受支持且可解码的音频格式；必要时压缩或拆分，确保**每个文件**不超过 11MB，同时整组有效人声仍不少于 30 秒。

**代表案例**：项目 `44125258879` 和 `69029141168` 分别把同一个跨项目 MP4 重复提交 7 次，每次都因单文件超限失败。

### 2.5 时长不可解析：2 次，1 个项目

**是什么意思**：系统找到了文件，但媒体探测读到的时长是 `N/A`，无法判断样本是否满足 30 秒要求。

**为什么会发生**：文件容器、编码、元数据或资产转存结果异常；这和“时长为 0”不同，是系统根本读不出可靠时长。

**重试是否有效**：原样无效。同一资产 `asset://a_d1PUCDK` 连续失败 2 次，没有观察到恢复。

**正确恢复**：对源文件重新转码，先做解码和时长 probe，确认得到确定的秒数后重新上传。系统应返回 `DURATION_UNREADABLE`，不要把它混成“样本太短”。

### 2.6 Provider timeout：9 次，2 个项目

**是什么意思**：样本输入已越过本地资产检查，但调用外部声音服务时超时。它不证明任务一定没有在 Provider 端创建或完成。

**为什么会发生**：外部服务响应慢、轮询窗口过短或瞬时拥塞。9 次失败集中在 2 个样本组，其中一个项目 `81326712529` 连续出现 7 次 timeout。

**重试是否有效**：**可以，但不能立即并发猛重试。** 两个样本组后来都使用相同样本成功，最快观察到的恢复间隔约 160 秒。这只证明暂时性故障可恢复，不代表每次 timeout 后原任务一定没成功。

**正确恢复**：先用 Provider task ID 或平台幂等键查询原任务；确认未完成后再按退避策略重试，例如逐步延长等待并限制最大次数。相同批次只允许一个恢复任务，避免 7 条台词同时重放。

### 2.7 结果缺失或不可解析：4 次，2 个项目

**是什么意思**：平台记录到了工具调用，但没有拿到可归类的最终结果。这里的真实状态可能是失败、仍在执行、成功但回执丢失，或日志关联失败。

**为什么会发生**：调用结果写入缺失、事件关联失败或返回结构不符合解析器预期。它首先是可观测性/状态一致性问题，不能直接算成 Provider 失败。

**重试是否有效**：不能从现有数据直接判断。两个样本组后来都成功，但这不证明原任务失败后被重试救活；也可能是原任务已经成功，只是本地没收到结果。

**正确恢复**：先按 tool call ID、Provider task ID 或幂等键查询状态和已有产物。只有确认没有成功结果且任务已终止，才允许重试；否则可能重复生成、重复计费或产生多个同名资产。

### 2.8 文本超过 5,000 字符：1 次，1 个项目

**是什么意思**：声音样本没有问题，但单条要合成的文本超过了接口上限。这不是克隆资产错误，而是 TTS 请求规格错误。

**为什么会发生**：长文没有在进入 `audio_produce` 前按段落或字符上限切分。

**重试是否有效**：原样无效。虽然同一样本后来有成功调用，但本次样本签名没有包含文本内容，不能据此声称“相同完整输入重试成功”；更合理的解释是文本被拆短或替换。

**正确恢复**：按语义段落拆分，每段控制在 5,000 字符以内，再逐段合成和拼接。产品错误提示应直接给出当前字符数和允许上限。

## 5. 资产地址不是稳定合同

完整窗口内有 `127` 次克隆调用把 `/projects/<另一个项目>/workspace/assets/...` 原始路径传入 `voice_sample_files`，涉及 `20` 个项目：

- `98` 次报资产找不到；
- `17` 次进入样本规格失败；
- `12` 次成功。

通过 `pexo_ods.projects.user_id` 核对，这 `127` 次全部发生在同一用户自己的不同项目之间，没有发现跨用户引用。因此当前证据不是越权泄露，而是**同一用户跨项目资产复用缺少稳定、明确的寻址合同**。

`12` 次成功又说明 runtime 不是统一禁止跨项目路径；同样的非 canonical 形态有时可解析、有时 NotFound。当前策略参考要求只传 `asset://a_xxx`，不要手工构造 `/projects/...` 路径，但生产边界没有 fail closed。

修复必须先做产品选择：

1. 若允许同用户跨项目复用：用稳定 asset ID 做 owner 授权和解析，不允许原始项目路径作为身份；必要时生成 import/copy receipt。
2. 若不允许：在预检阶段统一拒绝，并返回“先导入当前项目”的可操作错误。

无论选哪种，不能继续保留“原始路径偶尔成功”的模糊行为。

## 6. 类型和媒体语义也没有在入口收敛

- `11` 次失败调用把 PNG/JPG 等图像当作 clone sample，集中在 1 个项目；这是确定的类型错误。
- `33` 次失败调用直接传 MP4，涉及 8 个项目。MP4 可能含人声，但不应直接假定它是合格声音样本；应先显式提取音轨，再对音频 asset 做 MIME、解码、时长和大小校验。
- 代表例子：项目 `28788643549` 把两个角色参考 PNG 当作音色样本；项目 `04339290687` 把 `IMG_7994.mp4` 同秒提交 10 次。

这说明仅检查字符串“看起来像路径”不够。入口需要读取资产元数据和实际可解码流，而不能只依赖扩展名。

## 7. 根因链

1. **非 canonical 输入进入 runtime**：`voice_sample_files` 接受任意字符串数组，raw project path 和畸形 `asset://` 能进入工具。
2. **验证位置过晚**：资产解析、30 秒、11MB、时长解析检查在每个 TTS 调用内部执行，而不是在批量计划确认后、TTS 扇出前执行一次。
3. **没有 preflight receipt**：后续调用无法证明自己使用的是同一组已经通过验证的样本。
4. **没有失败熔断**：第一个确定性失败出现后，剩余同样本调用没有被取消或阻断。
5. **媒体类型没有收敛**：图片、视频和音频路径都能进入同一字符串字段；视频没有强制先提取音轨。
6. **跨项目复用语义模糊**：同用户跨项目 raw path 有成功也有失败，调用者无法形成稳定预期。

## 8. P0 修复合同

### 8.1 一次性预检

在批量克隆 TTS 前，对 sample set 只执行一次：

- 输入必须是 canonical asset ID；拒绝手工 `/projects/...` 路径和畸形 `asset://`。
- 校验资产存在、用户授权和明确的跨项目复用政策。
- 校验实际媒体为可解码音频；视频必须先走音轨提取，图片直接拒绝。
- 校验每文件 `<=11MB`、总时长 `>=30s`；记录超过 120 秒的自动裁剪区间。
- 返回 machine-readable reason code，不只返回自由文本。

建议 reason code：`ASSET_ID_INVALID`、`ASSET_NOT_FOUND`、`ASSET_ACCESS_DENIED`、`ASSET_NOT_AUDIO`、`DURATION_TOO_SHORT`、`FILE_TOO_LARGE`、`DURATION_UNREADABLE`。

### 8.2 生成可复用 receipt

预检成功后返回并保存：

- canonical asset IDs；
- sample set hash；
- owner/authorization 结果；
- MIME、codec、每文件大小、总时长、实际采用区间；
- validator version、创建时间和失效条件。

每条 `audio_produce` 必须绑定同一个 receipt，且请求中的 sample set hash 必须一致。不能让每条 TTS 重新解释一遍原始路径。

### 8.3 批量原子门禁与熔断

- preflight 未通过时，整批 TTS 为 `0` 次提交；不得部分执行。
- 同一 sample set 的确定性失败只记录一次，后续台词标记 `blocked_by_preflight`，不重复调用工具。
- 若 runtime 仍发现 receipt 失效，立即取消尚未开始的同批任务。

## 9. 验收标准

1. 给 10 条台词和一个不存在的 asset：产生 1 条预检失败、0 条 TTS、0 条 Provider 请求。
2. 给 10 条台词和 20 秒样本：同上，reason=`DURATION_TOO_SHORT`。
3. 给图片：入口直接 `ASSET_NOT_AUDIO`；不得进入时长解析。
4. 给 MP4：必须先形成独立音频 asset 和新 receipt；不得原样进入 clone sample。
5. 同用户跨项目资产：按选定政策 100% 稳定允许或稳定拒绝，不允许同形态时好时坏。
6. `precheck_failure_fanout` 指标应为 `0`；相同 sample set 的确定性失败调用数不得大于 `1`。
7. 线上监控拆分：preflight rejection、Provider failure、missing result 三类不得混算。

## 最终判断

这是 P0，不是因为单次报错有多严重，而是因为它位于批量生产的共享依赖入口：一个坏引用可以瞬间污染整批台词。最小可行修复不是再补一条 Prompt，而是把现有的 per-call 校验前移为**一次性、可绑定、可熔断的 sample-set preflight**。

本轮只做生产数据下钻和工程需求整理，未修改 Skill、Runtime、Provider 或 `tech-*`。
